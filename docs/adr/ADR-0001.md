# ADR-0001: Migrate to Full Microservices Architecture

**Status:** Accepted  
**Date:** 2026-04-30  
**Branch:** arch-change  

---

## Context

The platform currently runs as 3 backend services (user-auth, carBookingMicroservice, currencyConverter)
and a React frontend. Several architectural problems were identified:

1. **Car and Booking are co-located** in a single Spring Boot service (`carBookingMicroservice`), creating a false service boundary — they have separate bounded contexts and should be independently deployable.
2. **Frontend calls 3 different origins** (`localhost:8080`, `:8082`, `:8000`). CORS configuration is scattered across all services, there is no centralized rate limiting, and no single point for request logging or correlation ID propagation.
3. **Direct RabbitMQ publish in the request thread** is lossy — if the broker is unavailable at the moment of booking creation, the event is dropped and the customer read model in the booking service becomes inconsistent with no recovery path.
4. **Token storage in `localStorage`** exposes access tokens to XSS attacks. Production deployments require HttpOnly cookies and CSRF protection.
5. **No circuit breaker on the gRPC call** from booking to currency-converter. A slow or unavailable currency service causes booking requests to block for up to 5 seconds, creating cascading timeouts.
6. **No distributed tracing or Prometheus metrics**. Cross-service debugging requires grepping logs by hand with no correlation between services.
7. **Notifications** are not implemented — no email or log confirmation is sent when a user registers or a booking is created.
8. **CI/CD only exists for user-auth**. All other services are deployed manually.

---

## Decision

Migrate the platform in 8 incremental phases, each ending in a fully working and deployable state:

| Phase | Change |
|---|---|
| 0 | Pre-flight: structured logging everywhere, health probes on all services, toolchain version lockfile, ADR infrastructure |
| 1 | Split `carBookingMicroservice` → `carMicroservice` (port 8082) + `bookingMicroservice` (port 8083). Each gets its own PostgreSQL database (`cars_db`, `bookings_db`). Booking stores a car snapshot (brand, model, price at booking time) instead of a live FK — preserving historical accuracy after car deletion. |
| 2 | Add `notificationMicroservice` (Go): pure RabbitMQ consumer for `user.*` and `booking.*` events. Sends mock notifications to stdout; SMTP stub disabled by default. Manual ack + dead-letter exchange after 3 failed redeliveries. |
| 3 | Add `apiGateway` (Spring Cloud Gateway): single entry point on port 8080. JWT validation, CORS, Redis-backed rate limiting, correlation ID propagation, JWT claim forwarding. Frontend switches to one base URL. |
| 4 | Transactional outbox: booking service writes booking row and outbox event in a single DB transaction; a `@Scheduled` poller publishes outbox events to RabbitMQ asynchronously. Same pattern in user-auth (MongoDB session). Inbox event log in booking service for idempotent consumption and replay. |
| 5 | Resilience4j circuit breaker on gRPC client, HttpOnly cookies + CSRF, cursor-based pagination, OpenTelemetry distributed tracing (Jaeger), Prometheus metrics, JWT `aud` claim, RFC 7807 standardized error responses. |
| 6 | GitHub Actions CI/CD for all 7 services (path-filtered, Testcontainers integration tests, Trivy security scan, OIDC deploy to Azure Container Apps). |
| 7 | Full Azure deployment: Terraform IaC for Container Apps Environment, Cosmos DB (serverless), PostgreSQL Flexible Server, Azure Cache for Redis, Key Vault, Log Analytics, App Insights. |

---

## Consequences

**Positive:**
- True independent deployability: each service can be built, tested, and deployed in isolation.
- Single frontend origin eliminates scattered CORS config.
- Transactional outbox eliminates the message-loss window on booking creation.
- HttpOnly cookies remove the XSS token-theft surface.
- Circuit breaker prevents cascading failures when currency service is slow.
- Full observability stack (traces, metrics, structured logs) makes production incidents debuggable.

**Negative / Trade-offs:**
- Phase 1 introduces a synchronous HTTP dependency (booking → car service) that did not exist before. Car service availability becomes a booking creation dependency; mitigated in Phase 5 by circuit breaker.
- Transactional outbox adds latency between booking save and event publish (up to ~1s polling interval). Acceptable for this domain.
- API Gateway is a new single point of failure; mitigated by Container Apps auto-scaling (min 1 replica) and health probes.
- Total dev environment footprint increases (Redis, Jaeger, Prometheus, 2 extra services). Docker Compose resource usage grows accordingly.

---

## Alternatives Considered

- **API Gateway: Nginx reverse proxy instead of Spring Cloud Gateway** — rejected because Spring Cloud Gateway provides first-class JWT filter and Redis rate limiter as built-in features, avoiding custom Lua scripts and aligning with the existing Spring ecosystem.
- **Keep car and booking co-located** — rejected because the split is the explicit goal of this migration. The domains have different data models, deployment lifecycles, and scaling needs.
- **Event Sourcing for full event persistence** — deferred. The outbox + event log in Phase 4 provides replay capability sufficient for this project's scope without the full complexity of event sourcing.
