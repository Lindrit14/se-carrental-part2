# ADR-0003: API Gateway as Single External Entry Point

**Status:** Accepted
**Date:** 2026-04-30
**Phase:** 3 — API Gateway

---

## Context

After Phase 1 (car split) and Phase 2 (notification service) the platform has 5 backend services on 4+ different ports. The frontend tracks three base URLs (`VITE_AUTH_URL`, `VITE_BOOKING_URL`, `VITE_CURRENCY_URL`) and each service maintains its own CORS configuration. As we add more services this scales poorly:

- Browser-side configuration grows with every new service
- CORS must be configured identically in every service or preflight requests fail
- Rate limiting, correlation IDs and authentication are duplicated across services
- Backend services are exposed externally for the frontend, so the security perimeter is wide

## Decision

Introduce **Spring Cloud Gateway** on port 8080 as the only externally reachable backend. All other services become internal-only (no docker-compose `ports:` mapping; only `expose:` for inter-service traffic).

The gateway is responsible for:

1. **Routing** — `/api/v1/auth/**` → user-auth, `/api/v1/cars/**` → car-service, `/api/v1/bookings/**` → booking, `/api/v1/rates/**`+`/api/v1/convert/**` → currency-converter
2. **JWT validation** — RS256 with the shared public key
3. **CORS** — single source of truth (downstream services no longer need their own config)
4. **Rate limiting** — Redis-backed token bucket, keyed by client IP
5. **Correlation IDs** — generates `X-Correlation-Id` if absent, forwards downstream, echoes in response
6. **Claim forwarding** — extracts JWT claims into `X-User-Id` and `X-User-Roles` headers

Public routes (no JWT required): `POST /api/v1/auth/login`, `register`, `refresh`, `password/**`, `GET /api/v1/cars/**`, `/healthz`, OPTIONS preflight.

## Consequences

**Positive:**
- Frontend has a single base URL (`VITE_API_URL`)
- New services need zero frontend changes (just a new gateway route)
- Cross-cutting concerns (auth, rate limiting, tracing) live in one place
- Production attack surface is one ingress, not five

**Negative / Trade-offs:**
- The gateway becomes a single point of failure. Mitigated in Phase 7 by running multiple replicas behind Azure Container Apps' built-in load balancer.
- Downstream services still validate JWTs themselves (defense in depth) — there's a small duplicate-validation cost per request. Could be removed later if we move to a fully internal-trust model.
- Direct `curl http://localhost:8082/...` no longer works during dev. Use the gateway URL or `docker compose exec` for ad-hoc debugging.
- Rate limiting is per-IP rather than per-user. Authenticated rate limiting is a Phase 5 concern.
