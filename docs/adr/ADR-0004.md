# ADR-0004: Transactional Outbox Pattern

**Status:** Accepted
**Date:** 2026-04-30
**Phase:** 4 — Outbox

---

## Context

Before Phase 4, both the user-auth and booking services published domain events to RabbitMQ inline with their use case logic:

```go
uc.users.Create(ctx, u)
_ = uc.publisher.Publish(ctx, event)  // RabbitMQ down? Event silently lost.
```

This has two failure modes:

1. **Lost events** — if RabbitMQ is unavailable, the publish call fails after the domain write has succeeded. The booking service's previous code didn't even check the publisher's error. The user is created, the booking is saved, but no consumer ever hears about it.
2. **Phantom events** — if the publish call succeeds but the surrounding transaction rolls back (e.g. a downstream error), consumers see an event for state that was never persisted.

Both are at-most-once semantics in a system that needs at-least-once.

## Decision

Adopt the **transactional outbox** pattern in both services.

### Booking service (Java/Postgres)

- New `outbox` table written in the same JPA transaction as the domain change.
- `OutboxEventPublisher` implements `EventPublisher` with `@Transactional(MANDATORY)` so every event must be enqueued from inside an open transaction.
- `OutboxRelay` (`@Scheduled(fixedDelay=1000)`) drains unpublished rows to RabbitMQ using `SELECT ... FOR UPDATE SKIP LOCKED` so multiple replicas can run safely in parallel.
- A separate `event_log` table (the inbox) gives idempotent consumption of incoming `user.*` events: `event_id` is unique-constrained, so a redelivered message is recognised and skipped.

### User-auth service (Go/Mongo)

- New `outbox` collection with a unique index on `event_id` and a partial index on `(occurred_at)` filtered to unpublished rows.
- `outbox.Publisher` implements `ports.EventPublisher` by inserting into Mongo. Use cases never touch RabbitMQ.
- `outbox.Relay` polls every second and publishes pending events.

## Consequences

**Positive:**
- At-least-once delivery for every event the platform produces.
- Operations decouple from RabbitMQ availability — restart RabbitMQ and pending events drain automatically once it's back.
- Replay capability: re-publishing from `outbox` (or re-processing from `event_log`) is now a SQL operation.

**Negative / Trade-offs:**
- **Standalone Mongo cannot multi-document-transact.** In dev, the user document and outbox row are written sequentially; if the second write fails the user exists without a corresponding event. Production runs against a Cosmos DB / replica set where `WithTransaction` could be added if this trade-off becomes intolerable.
- **Latency.** Events take up to one poll interval (currently 1s) to reach RabbitMQ. Acceptable for the events we publish today (welcome emails, audit logs); unsuitable for low-latency request/reply flows — those should stay synchronous.
- **Storage growth.** Outbox tables grow unbounded. A future archival job should move rows older than e.g. 30 days to cold storage (Phase 5+).
- **Single-instance assumption (user-auth Relay).** The Go relay does not lock rows, so running multiple user-auth replicas would publish duplicates. Mitigated by event consumers' inbox-based idempotency, but a Mongo `findAndModify` lease could be added if we scale out.
